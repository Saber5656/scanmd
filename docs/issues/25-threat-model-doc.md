# Title

SECURITY-MODEL.md: full threat model mapped to code

## Summary

Write `docs/SECURITY-MODEL.md` — the complete threat model expanding DESIGN §10 — and
verify every stated control against the actual implementation, fixing doc-vs-code drift
or filing issues for real gaps found.

## Context

DESIGN §10 is the normative summary; this document is the audit-grade expansion the
public repo links from `SECURITY.md`. Writing it after waves 0–4 exist turns it into a
verification pass, not aspirational prose.

## Scope

- `docs/SECURITY-MODEL.md` (new), one-line link additions to `SECURITY.md` and DESIGN
  §14. Code changes only if drift-fixes are trivial (< 10 lines); otherwise file issues.

## Detailed Requirements

1. Structure (all sections required):
   - System overview + data-flow diagram (ASCII) with trust boundaries B1–B7 drawn.
   - Assets: captured content (primary), user file system, clipboard, TCC grants,
     config file, release artifacts.
   - Trust boundary table: for each of B1–B7 (DESIGN §10.1): threat scenarios
     (STRIDE-tagged), implemented controls **with code references**
     (`file.swift:symbol`), residual risk, test reference.
   - Abuse cases (DESIGN §10.7) with positions.
   - Privacy rules p1–p4 with their enforcement points (Log wrapper signatures, temp
     file lifecycle, no-network CI guard).
   - Permissions model (§10.3) incl. TCC attribution notes for CLI vs app
     (ADR-004/KU-2 outcomes as actually measured in Issues 15/16).
   - Supply chain (§10.6): dependency inventory with pinned versions, workflow
     permissions inventory (generated by listing every workflow's `permissions:`), 
     release integrity chain (checksums → Developer ID → notarization).
   - Resource-limit table (§10.4) with enforcement sites.
   - Out-of-scope threats (compromised local account, kernel, malicious Homebrew tap
     mirror, etc.) stated explicitly.
   - v2 security work: sandboxing plan, LLM formatter threat delta (from ADR-003).
2. Verification pass (the core of this issue): for EVERY control row, run/inspect the
   referenced code or CI job and mark ✅ verified / ❌ drift. Each ❌ → trivial fix in
   this PR or a filed GitHub issue referenced in the row (no silent gaps).
3. Cross-check the Issue 02 `SECURITY.md` reporting flow still matches reality; add the
   link to this document.
4. Keep DESIGN §10 authoritative for *requirements*; this document records *implemented
   state + analysis*. Divergences between the two must land as DESIGN edits in the same
   PR (flagged for review).

## Acceptance Criteria

- [ ] All sections present; every B1–B7 row carries a code reference and a
      verified/drift mark; zero unresolved ❌ without a linked issue.
- [ ] Workflow-permissions inventory matches every `.github/workflows/*.yml` at merge
      time.
- [ ] Dependency inventory matches `Package.resolved` + `App/project.yml` pins exactly.
- [ ] `SECURITY.md` links here; DESIGN §14 table row updated.

## Validation

Reviewer spot-checks 3 random control rows against code; CI green; drift issues (if
any) linked in the PR description.

## Dependencies

Soft: Issues up to 23 merged (verification needs real code). Can start drafting from
DESIGN §10 any time; must not close before waves 0–4 are merged.

## Non-goals

New security features, penetration testing, sandboxing work (v2).

## Design References

DESIGN §10 (all), §14; ADR-003, ADR-004, ADR-005; ISSUE_PLAN KU-2/KU-5 outcomes.
